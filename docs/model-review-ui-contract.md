# 模型博主测评：界面契约与当前口径

本包（`@scitiger-ai/lwb-model-review`）三页——题库 / 开始测评 / 历史任务——的视觉系统、组件规格与题库口径。生效代码是 `lwb/packs/model-review/client.js`，下文的文件路径都相对该目录；界面的历次分析与实施流水账见 Git 历史。

## 设计原则

1. **对齐官方壳，不自建第二套外壳**：颜色、间距、圆角、暗色全部走 `--lwb-*` 令牌；官方对话与右侧栏保持原件。
2. **页面密度服从任务**：测评页是「配置 → 发起 → 观察」，配置必须一屏完成；历史与题库是「浏览 → 定位 → 展开」，列表必须高密度。
3. **归属色与操作色分离**：色彩表达「我在哪一页」和「这是什么状态」，不再表达「这里可点」。
4. **每个数字都要能被解释**：耗时、模型数、产物数都要可比较；没有数据的模型不装样子。
5. **增长优先**：按 100+ 题目、500+ 任务、20+ 模型设计，超量走抽屉 / 折叠 / 分段。
6. **暗色同源**：所有新增色令牌同时给出 `body[data-ds-dark-theme]` 值。

## 视觉系统

### 三层色

```text
归属色（我在哪一页）    题库 violet · 开始测评 orange · 历史 cyan
交互色（可以操作）      --mr-brand #4f46e5 / --mr-brand-soft #eef2ff
状态色（当前状态）      success 绿 #16865f · running 蓝 #2869d8 · waiting 琥珀 #a56c19
                        danger 红 #a33 · neutral 灰 --lwb-muted
```

归属色沿用导航已生效的值，保证「导航里是紫的，进去也是紫的」：

| 令牌 | 亮色 | 暗色 | 来源 |
|---|---|---|---|
| `--mr-violet` / `-soft` | `#8b5cc4` / `#f2ebfb` | `#c4a7ff` / `#31263f` | 导航 `data-tone="violet"` |
| `--mr-orange` / `-soft` | `#cf762b` / `#fff0e4` | `#f6bd7c` / `#3e3024` | 导航 `data-tone="orange"` |
| `--mr-cyan` / `-soft` | `#2579b9` / `#e7f4fb` | `#7cc4ee` / `#1d4058` | 对话模块色（蓝与交互色同族会混，故取青蓝） |
| `--mr-shadow-sm` | `0 1px 2px rgba(15,20,25,.04)` | 同 | 对齐口播包 |

### 状态色（运行卡片与列表）

| 状态 | 顶条 | chip | 附加 |
|---|---|---|---|
| queued 等待中 | `--lwb-line` | neutral | — |
| running 进行中 | `--lwb-blue` + 呼吸动画 | info（蓝） | 卡片头部显示已用时 |
| succeeded 已完成 | `--lwb-green` | success | 耗时 + 产物数 + 回答字数 |
| failed 失败 | 红 `#c25f4a` | danger | 卡片头部即显示错误首行；可带 `续跑` 标 |
| cancelled 已取消 | neutral | neutral | — |

`running` 的呼吸动画只作用于顶条与一个 6px 圆点，`prefers-reduced-motion` 下停用。

### 状态由回合结束原因决定，不由「有没有文字」决定

一次运行产出文字**不等于**跑完。模型先写了一半、随后服务商返回 `429 engine overloaded` 而结束回合的情况真实存在；若按「有回答即成功」判定，这样的尝试会被记成「已完成」，报告读起来就像一个正常但话少的模型——用来比较模型时会误导。

判定取自会话日志里该回合的 `turn/end.reason`：

| 回合结束 | 运行状态 | 说明 |
|---|---|---|
| `completed` | succeeded | 唯一记「已完成」的情形 |
| `max-tokens` / `length` | failed | 输出被截断，工作未完成 |
| `error`（如 429 / RATE_LIMIT） | failed | 保留已产出的文字与产物，错误原因随行 |
| `aborted` / `cancelled` | cancelled | 用户主动停止，不算模型失败 |
| 无 `turn/end` | failed | 回合未闭合 |

### 「续跑」标记（`续` / `续跑`）

首次尝试失败后，用户仍可从卡片继续对话（如手动发「请继续」）。这类运行的耗时、token 与产物覆盖的已不只是测评包自己那一次尝试，于是状态可能停在 `failed` 而产物却很完整——不加说明会像报告自相矛盾。

宿主据此在运行记录上写 `continued: true`（判据：投影的 `asOfSeq` 已越过记录里的 `asOfSeq`，即会话确实往前走了，而非首次补读）。报告在状态列、矩阵格与运行卡片上标 `续` / `续跑`，并在口径页解释：其耗时与 token 含续跑部分，回答快照仍停在首次结束时刻。

## 高度归属（历史任务列表）

宿主给能力页只有**一个滚动容器**（`.lwb-overlay-body`：`flex:1; min-height:0; overflow:auto`）。报告条是进入报告的唯一入口，它要一直在画面底部，这件事由**两半**拼成，缺一半都不行：

- **拉住（sticky）**：`.mr-pickbar` 加 `position:sticky; bottom:0; z-index:6`，阴影朝上，与开始测评页的启动条同一套排布。它只在页面比窗口高时起作用——`bottom:0` 把已经落到视口下方的元素**拉回来**，永远不会把元素**推下去**。
- **吃掉剩余（measured fill）**：列表拿走滚动视口剩下的高度，`--mr-list-fill` 就是这个数字，由 `useViewportFill` 量出来。

只有 sticky 的时候，列表的整行窗口（482px）让页面比高窗口矮，滚动条不存在，sticky 无从生效，报告条就停在面板下沿：1615×1180 下条底距窗口底 159.8px，只剩面板底边到窗口底那一整条留白。

**怎么量**（`useViewportFill`）：从列表往上找最近的可滚动祖先（`overflowY` 为 `auto`/`scroll`，**不认宿主类名**），再算

```text
leftover      = 视口 clientHeight − (页面自身底边到视口顶边的距离 + 视口 scrollTop)
--mr-list-fill = 列表当前高度 + leftover          （向下取整，绝不进位）
```

- 量的是**元素的边**，不是与壳同步的常数：窗口高度变了、页面滚过了、宿主换壳都不影响。`scrollHeight` **不能**用来做这件事——它永远不会小于视口，所以"页面太矮"和"页面正好铺满"在它眼里一样（第一版就是这么写的，实测填充值恒等于列表当前高度，页面上毫无变化）。
- 向下取整：高半个像素的页面会长出一条什么也看不到的滚动条。
- 页面的底边取 pack 自己的 `.mr-page`（`Frame` 的 `rootRef`）：**实测宿主给能力页的容器在真壳里是撑满视口的**（它自己的 `min-height:100%` 在这个上下文里会解析），所以容器盒的高度不能当作内容高度。预览壳的 stand-in 与真壳在百分比解析上并不等价（同一个容器在预览里不撑），这类"内容盒与容器盒"的判断只能在真壳结构里做。

**floor 不动**：`--mr-list-floor` 仍是 482px（窄屏 422px），`max-height:max(var(--mr-list-floor),var(--mr-list-fill,0px))` 取两者较大值；`min-height:max(300px,var(--mr-list-fill,0px))` 让只有两条任务的页面也把面板落到窗口底。窗口矮到连 floor 都放不下时，列表保持 482px、页面照旧滚动、报告条照旧被 sticky 钉住——"用更短的页面换更短的列表"仍然是错的交易。

**页底那 52px**：宿主给每个能力页 `padding-bottom:52px`。历史任务页的最后一行是贴底工具条，所以这一页自己把它拿走（`.lwb-page-capability:has(.mr-page[data-tone="cyan"]){padding-bottom:0}`）——只认自己的归属色，题库页与测评页的页脚不动。留着它，条就会停在窗口下沿上方半个页脚的位置。

实测（真 React + 宿主原样的壳 DOM/CSS + 28 条任务，用一次性的实时驱动跑出来；驱动不属于本包，见下）：

| 窗口 | 列表高度 | 滚动视口 | 条底到窗口底 |
|---|---|---|---|
| 1615×1180 | 675（fill） | 1133，不溢出 | 4.3px |
| 1691×1250 | 745（fill） | 1203，不溢出 | 4.3px |
| 1615×900 | 482（floor） | 853，溢出 | 0（sticky 钉住） |
| 1280×700 | 482（floor） | 653，溢出 | 0（sticky 钉住） |
| 拖动窗口 1250→900→1400→1250 | 745→482→895→745 | — | 4.3 / 0 / 4.3 / 4.3 |

**仍然不要**改由页面接管容器高度（`height:100%` + `1fr` + 列表 `flex:1`）。pack 页面挂在 `.lwb-page-capability` 之下**两级**——宿主在中间还有一个无类名的包裹 `div`（`h('div', {key:'capability'}, h(CapabilityPage, …))`）。百分比/`flex` 链在那里断掉：`.mr-page` 拿不到高度，面板行退化为 `min-content`，列表被压到下限而页面下方留出空白。填充是**量出来的高度**，不是继承来的高度，这条界线要守住；`data-fit` / `data-scroll` 那类与宿主包裹层级耦合的机制一律不要。

**空态与加载态不参与填充**：没有行就没有可增长的列表（`.mr-empty` 是固定高度的虚线框），这时报告条跟着短面板走。要改是另一件事——把填充目标从列表换成面板。

**列表可以停在半行**：floor 保证整整 8 行（窄屏 7 行），填充值却是量出来的任意高度，所以列表底部可能是半行——这正是"下面还有内容"的提示。

预览壳（`test/preview.mjs`）必须复刻这个滚动容器：以前它随页面长高，所以截图里永远看不到折叠。但它只做**一次序列化渲染**——ref 不会挂上、effect 不会跑——所以**静态预览看不到填充**，`history.html` 里的列表仍是 482px。要看填充，只能让真 React 在宿主原样的壳里跑一次：临时用 esbuild 把 React 与一个 `window.__ModuleLoader__` 垫片打成一个 bundle，把 `client.js` 当普通脚本加载，页面的壳 DOM/CSS 从 `lwb/dsh-bundle/client.js` 里原样抄出来（`.prototypes/mr-live/` 就是这么做的，不随包提交），或用真机。

## 启动确认（开始测评）

`api('start')` 只有一处调用点——测评页的启动条。它会调用所有已选模型、记录用量，并且**不会打断**已在运行的任务；因此点击是页面最后一次能发问的机会，与 AI竞技台「开始新的比赛？」同形：

- 计数取自 host 任务列表，且**在点击时重读一次**（`api('tasks')`），因为本页只轮询当前显示的那个任务：页面自己那份 `tasks` 可能把刚结束的任务算成进行中，也可能漏掉别处新起的任务。重读失败就用页面已有快照，不阻断发问。
- `notice` 仅在有未完成任务时出现：`已有 N 个测评任务进行中（含本页正在查看的这个）。继续开始将并行运行一次新测评，它们不会被打断。` 计数含本页正在查看的那个，与竞技台口径一致。
- `summary` 是最后一次复核点：题目 + 模型清单（超过 4 个显示前 4 个 + `等 N 个`）。
- 出口是 Escape、× 和 取消；**遮罩点击不关闭**。遮罩正好盖住触发它的按钮，否则双击的第二下会开了又问「不」。
- 层级 100/101，高于抽屉的 90/91：把题目交接过来的抽屉可能还开着。Tab 圈在框内三个按钮之间；关闭后焦点还给触发控件；已有待决确认时再问一次直接返回 `false`，不叠框。
- 启动成功后若仍有进行中的任务，提示补一句「正在进行的任务在后台继续，可在「历史任务」中查看。」

## 测评报告（勾选导出）

历史列表每行左侧一个勾选框，「已结束」的任务才可勾——正在跑的 run 会被冻结在半途，报告会写下一个还没结束的耗时。

- **含失败模型的任务仍然可勾。** 任务级状态是"任一模型失败即 failed"（`model-review-store.mjs`），按"已完成"过滤就恰好复盘不了「4 成功 1 失败」这种最该看的任务；失败的模型在报告里占一行并带错误原因。
- 勾选框**在行按钮之外**，不嵌在里面：控件嵌在 button 里是非法标记，Chromium 下它的点击会触发两次。
- 两个出口共用一份文档：`导出测评报告` 下载，`在工作台内查看` 把同一份 HTML 装进 blob URL 的 iframe。预览与导出**逐字节相同**，没有第二套排版。

报告结构：页头口径声明 → **总览矩阵（N 题 × M 模型 + 合计行）** → **分题明细（pill 形 tab，`flex-wrap` 换行，不是横向滚动）** → 每题：判点（题目快照原文）→ 事实表 → 产物直接运行 → 页脚口径。

- **数字全部来自宿主投影**（`sessionStats` / `tokenUsage` / `contextPressure`），写入 `run.stats` 并冻结在运行结束时刻，`run.stats.asOfSeq` 就是那一刻的会话日志序号，报告里作为「冻结位置」显示。新 run 在结算时捕获；**老任务在首次生成报告时补读一次并落库**，标 `source: 'backfill'`、报告里带「补」标记——因为它可能包含了运行结束之后继续对话的增量。
- **没有数字时必须说清是哪种"没有"。** 取不到数字有五种原因，读的人的下一步动作完全不同，所以它们各有各的说法，报告顶部按原因归组给出次数与「能不能补」：

  | 原因 | 含义 | 能不能补 |
  |---|---|---|
  | `unsupported` | 当前工作台版本不支持读取会话投影 | **重启/升级工作台后重新生成即可补齐** |
  | `failed` | 读取会话投影失败 | 稍后重新生成即可 |
  | `empty` | 投影里没有耗时与 token | 该会话没有记录这两项 |
  | `missing` | 该会话的投影已被清理 | 无法补齐，只能重跑 |
  | `no-session` | 该运行早于独立会话的测评 | 无法补齐，只能重跑 |

  落库规则与"能不能补"一致：**可补的原因只报告、不落库**（`RETRYABLE_STATS_REASONS`），不可补的原因写进 `run.statsUnavailable` 并被后续读取直接短路。把"重启就能修"记成关于这次运行的永久结论，是这套区分存在的全部理由——它源自一次真实误判：宿主没重启导致 `stats` 静默为空，而报告只写「未记录」，看起来和"数据已经没了"一模一样。`stats` 路由返回 `{ stats, reason }`，恰好一个为 null。
- **投影的 wire 值不等于它落盘的 state。** 读取时必须按宿主交出来的形状解析：`tokenUsage` 的 wire view 是 `state.totals`（四个桶在顶层），而缓存里存的是 `{ totals, last }`；`sessionStats` 与 `contextPressure` 的 wire 与 state 同形。曾经只读 `.totals`，于是**真机上所有数字为空、而 81 个测试全绿**——因为夹具和缓存文件都恰好是 state 形状，验证的是我的假设而不是宿主的契约。现在两种形状都接受，并且有一条断言要求它们读出同一组数字。
- **模型缺失格显示 `—`，不是失败**；同题被勾选多次标「第 N 次」。
- **不排序、不做热力着色**：颜色只表达成功/失败。合计行只是把同一模型的事实相加，报告里明写"不是得分，也不能用来排名"。
- 口径必须随报告一起给出：总耗时含工具与排队；解码速度是纯解码；缓存命中分母是 prompt 三桶之和；上下文占比是**最近一次请求**的估算压力。
- **产物三个一行。** 整宽堆叠时一屏永远看不到两个结果，而"对比"正是这个报告存在的理由。`repeat(3, minmax(0,1fr))`，≤900px 退两列、≤620px 退一列；`align-items:start` 让没有产物的卡片不被拉高。
- **舞台跟列宽走，不写死高度。** `.art-stage{aspect-ratio:16/10}`：原来 430px 的固定高度是按整宽定的，缩到 1/3 宽之后盒子大半是空的；产物本来就按宽度绘制，用比例才能让每张卡的画面形状一致。
- **一个 run 只占一格。** 一个 run 可能写两个页面（比如场景 + 外壳），第二个不再叠一个舞台，而是留成可点开的预览按钮——否则那一格双倍高，把网格的行拆了。卡片里的顺序与产物列表一致（列表里第一个就是舞台上那个）。
- 卡片的**标题只出现一次**：模型名在卡片头，产物头只放文件名与体积，不再重复。
- **只有 HTML 产物内联**（单个上限 4 MB，超过只登记）：这一批实测 46 个产物里 45 个是真正的单文件，内联后报告约 4.4 MB。截图与代码只列名字和体积——68 张截图有 30 MB，内联会让报告失去可分享性。
- 产物在**沙箱 iframe** 里运行，只给 `allow-scripts`（+ `allow-pointer-lock`），**不给 `allow-same-origin`**：两个都给的话同源产物能自己摘掉沙箱。产物之间互不可见，也访问不到报告本身。
- 只渲染视口内的产物（`IntersectionObserver`，±120px），滚出去或**切换 tab 即卸载 iframe**——否则 28 个用 `requestAnimationFrame`、16 个带 canvas、5 个 WebGL 的产物会一直烧 CPU。三列之后同屏会有三个产物在跑，所以余量从 ±250px 收到 ±120px：够覆盖即将滚进来的那一行，不会多挂一整屏。
- 弹窗预览另开一个 iframe 实例，点空白、Escape、关闭按钮都能关，关闭时销毁。

分工：**报告在客户端组装**（视觉系统本来就在 `client.js`，`ReportBuilder` 是纯函数、可被 harness 渲染测试），host 只按 `(taskId, runId, path)` 提供产物正文。

## 边界与契约

- **不动**官方对话、官方右侧栏、`focusSession` / `renderConversation`、`RunCard` 与 `useAutoFocus` 的签名；卡片外壳可重做，对话区不能动。
- `test/client-runtime.test.mjs` 绑定若干语义与结构断言（`官方右侧栏`、`记录 N 个产物`、`这条历史任务没有保存会话标识，无法回看对话过程。`、`已接回正在执行的测评任务`、`useAutoFocus`、`data-active`、`onPointerDownCapture`）；改界面时保留这些语义。
- 后端新增两个接口：`stats` 取一次运行的投影数字（老任务一次性补读并落库），`artifact` 读一个已登记产物的正文。其余仍用 `answer` / `completedAt` / `artifacts`，题库使用次数用 `tasks` 现算。
- 决策口径：历史任务为「列表全宽 → 详情全宽」；模型选择器为分组紧凑行；对比视图进 v1；题库分类保持扁平自由文本；模型上限保持 4；页头 kicker 用「并行测评 / 题目资产 / 测评档案」；开始测评必须先确认，进行中的任务在确认框里点名。
  **仍然不引入 `score/verdict`**：报告只陈述宿主已经算好的事实（耗时、token、缓存命中、上下文占比），不排序、不评优、不打分，判断留给用户。2026-10-01 那条「评分/结论维度不纳入本次」的结论继续有效——本次做的是事实报告，不是评分维度。
- `test/render-harness.mjs` 的 `click` 会先结算待处理的状态变更再找控件：这个 hook 引擎只在 `settle` 要求时重渲染，而浏览器会先重渲染。少了这一步，测试点到的是上一轮闭包里的控件（例如 `selected` 还是空的那个启动按钮）。`change` 是它的对应物：勾选框走 `onChange`，`click` 够不到。harness 的 `URL.createObjectURL` 会把 blob 内容记进 `blobs`，这是测试唯一能读到导出文档的地方。
